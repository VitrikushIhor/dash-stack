Confirmed on 2026-10-09: removing a never-published exercise offers keep-as-private/delete; the owner can copy their own unpublished draft into a topic; an owner can logically delete an eligible blocked test through a metadata-only action without recovering its content or erasing moderation evidence.

Subsequent decisions recorded on 2026-10-12: blocked-topic deletion requires no moderator approval/new review and kept exercises retain blocks; guest reload/leave resets the attempt, sign-in warns without transfer, and opening binding expiry is 24 hours; own published sources offer publication/draft choice with publication default, and public topic exercise pages support independent copying.

## 1. State is several independent facts

Do not implement one resource enum that conflates drafts, publication, visibility, moderation and deletion. A public test may have unpublished edits and an active block simultaneously.

| Fact             | Source of truth                                           | Consequence                                                                |
| ---------------- | --------------------------------------------------------- | -------------------------------------------------------------------------- |
| Ownership        | Authenticated user and resource owner                     | Author rights; no organization role fallback                               |
| Editable content | Draft and optimistic revision                             | Only explicit publication changes visitor content                          |
| Publication      | Current immutable version pointer                         | Absence means no normal learner start, even if visibility is public        |
| Composition      | Desired draft membership and current published membership | Removing from a draft does not remove current public access                |
| Visibility       | Standalone resource or parent topic                       | Private, unlisted or public; changes immediately                           |
| Moderation       | All effective active restriction targets                  | Any applicable block denies ordinary content access                        |
| Deletion         | Logical deletion marker, later physical cleanup           | Immediate ordinary access denial; retained bytes are not access permission |
| Attempt state    | Principal, fixed version, revision, status and deadline   | Saved content and an old ID do not override current access                 |

`DRAFT_ONLY`, `PUBLISHED`, `PENDING_REMOVAL` and `DETACHED` below are explanatory labels derived from those facts, not proposed additional database status columns.

For an embedded exercise, both its own restrictions and its parent topic's restrictions apply. A source test's later ordinary changes do not affect an independent copy. Only an explicitly authorized moderation operation can apply restrictions across its lineage.

## 2. Policy evaluation and denial precedence

Each operation uses an explicit policy; authorization on a parent resolver or UI button is insufficient. Ordinary reads/mutations apply this order internally:

1. Validate request structure and establish the caller/session or guest capability. Authentication infrastructure failure is an error, not a guest fallback.
2. Resolve the relevant test/topic/attempt and bind IDs to their actual owner and parent/version. A supplied owner ID never grants authority.
3. Deny ordinary access to deleted resources or deleted parents, regardless of retained versions.
4. Deny ordinary content access if any effective test/topic restriction is active, including for the owner.
5. Check operation-specific ownership or current visibility/publication membership. A normal user with a platform role still follows these checks on ordinary endpoints.
6. For attempt/result operations, require the caller's own attempt, matching version membership, an allowed status and an unexpired deadline.
7. For writes, check expected revisions and operation identity, recheck access under the mutation's concurrency protocol, then commit all related state and the receipt together.

Internal denial precedence does not justify revealing private existence or moderation details. Unknown and inaccessible content use a safe non-disclosing response for unauthorized callers. Owners can receive the agreed blocked notice/reason without content. A public topic may show a blocked-exercise placeholder without its prompt, media or answer data.

Privileged moderation and metadata-only lifecycle commands use separate policies. They do not call an ordinary content endpoint with a global `ignoreAuthorization` flag. Unresolved operations are not exposed until their policy is decided.

An unlisted link grants reading/taking, not ownership, draft access or a new right to copy another author's unlisted test. The agreed external copying source is a public test. Public catalog/library endpoints must apply their own policy before returning rows, totals or media; no embedded exercise cards in the public test catalog.

For a new start, resolve the current test version from the standalone publication or the current topic publication's exercise entry. For a continued attempt, use its pinned version while checking today's resource access. Do not require its version to equal the current version, and do not permit arbitrary historical-version browsing.

## 4. Resource and composition transitions

Author content edits use explicit “Save draft”, including topic materials and desired exercise ordering/composition. Typing or reordering alone sends no draft-save mutation. Until acknowledged, edits are local and marked unsaved. Save and publish are distinct: publication uses a saved server revision and is unavailable while the editor is dirty, saving or conflicted. Existing explicit resource commands (creation, copying, visibility and confirmed deletion) keep their own semantics; they must not silently submit or discard other unsaved editor content.

On a stale save, keep the local inputs in the current tab, report the conflict and offer loading the latest draft with a discard warning. Do not auto-merge, force overwrite or silently replace the expected revision and retry local content. Warn before leaving/reloading a dirty editor; no persistent local recovery is introduced. If the author edits while a save is in flight, its acknowledgment covers only the submitted snapshot; newer local edits remain dirty. Learner answers follow the separate submit-only policy.

Publication atomically consumes one coherent topic draft. A save racing with publication either participates in that revision or conflicts; it cannot publish only half an exercise edit. A failed topic publication changes none of its visitor-visible content or detachments.

Topic deletion includes draft-only and pending-removal members, but not already detached standalone tests. Coordinate membership changes with deletion; a stale count is not approval to silently affect a different set. The confirmation explains that originals and independently owned copies/media survive.

For removal of a never-published exercise, the confirmation explains both choices and that its source/independent copies are unaffected. Check the never-published condition again under the topic publication/membership lock: a concurrent publication cannot convert this into immediate deletion of a now-published exercise. Return a conflict and refresh the action when that precondition changes.

An owner can choose their own unpublished test as a copy source. For an already-published own test, offer published version (default) or current draft. Copy the selected coherent snapshot, including incomplete draft content when chosen, through source/destination revision and media authorization checks. Another author's public source allows only the current publication. Public topic exercise pages offer “Add to my topic”; their published source is the exact exercise version in the current topic publication. The new exercise is an independent draft and cannot be published until valid. A changed selected source revision/version conflicts rather than silently substituting another snapshot. O-09 product choices are resolved.

Blocking is not a content edit. If a currently published exercise is blocked, its position becomes a safe unavailable placeholder immediately; other accessible exercises/materials remain accessible. Do not fetch the blocked body merely to render that placeholder. Reject topic publication while its desired draft composition contains a blocked exercise; identify the entry using safe metadata without exposing blocked content. The author may exclude it through metadata-only draft composition changes and publish the remaining valid content, provided the topic itself is writable and unblocked. Already-published blocked exercises become unavailable immediately while other accessible exercises/materials remain usable if the topic is not blocked. Exclusion/detachment never lifts the test restriction. Removing the blocked entry through metadata-only composition changes must never clear its own restriction.

## 5. Attempt transitions and deadlines

Create a completed attempt only on successful whole-test submission. Before submission, answers exist only in the current tab: no server answer saves, active-attempt rows, cross-device recovery or learner-save conflicts. Each tab is independent. Opening returns an authorized server-verifiable binding to the displayed immutable content/scoring version without creating an attempt. Submit all current answers and that binding; recheck current access and atomically validate, evaluate, persist the completed attempt/result and minimal operation receipt. Failed submission preserves local answers and creates no partial attempt. Warn before leaving with unsubmitted answers; closing/reloading loses them. Local “Start again” confirms clearing local inputs rather than superseding server state. Retain authenticated results for three days from submission, without renewal on reads/retries. Repeat of the same submit operation cannot create another completion. The former 14-day unfinished retention and one-active-attempt constraints are superseded.

Retain minimal successful-operation receipts for 12 hours from commit, without answer bodies or authored content. A signed ticket binds principal, operation, resource, nonce, canonical payload hash, issue time, admission deadline and key version. Admission lasts 12 hours. A committed receipt permits an authorized replay for 12 hours from commit, even after admission ends. Replays do not renew either deadline or extend result retention. Recheck current access before retrieving the referenced result; a changed payload conflicts. If admission expires without a receipt, or the receipt expires, reject without re-execution.

For guest operations, derive the opening capability by domain-separated HMAC from opening ID and the original ticket nonce. Derive the result capability in a separate HMAC domain from attempt ID and the submit ticket nonce. Store only capability hashes; same-ticket retries derive the same capability, while another ticket or resource ID alone cannot recover it. Keep raw capability only in current page memory, never URL, logs, localStorage or sessionStorage. Keep signing keys until tickets and receipts issued with them pass their replay windows. These semantics are agreed; implementation and transport/security verification remain required.

The authorized open-page version binding expires 24 hours after opening for both registered users and guests, without renewal by typing, polling or retries. Retain its immutable version/media for the eligible binding lifetime without storing pre-submit answers or an attempt. Submission within the window evaluates the bound version despite ordinary republication; current access/block/deletion checks still prevail. After expiry require reopening the test and warn that the old page can no longer submit. Guest completed results expire 24 hours after successful submission, without renewal on reads/retries, and are accessible only through the same open page. Close/reload/leave loses access with no restoration. Current blocking/visibility/deletion checks may deny access earlier. Enforce expiry before hourly cleanup removes answers/results. This result clock is independent of the 24-hour opening-to-submission binding clock; successful submission must authorize page-only result access without silently extending the submission binding.

Guest answers/results remain page-only with independent tabs, no persistent recovery and no transfer at sign-in. Version-binding lifetime is fixed at 24 hours from opening; guest results expire 24 hours from submission; the former activity-renewal mechanism does not apply.

After a source author deletes their account, independently owned copies remain usable under their own access/restriction rules. Render source attribution as “Deleted user” without an avatar or profile link, and remove stored source-author display-name snapshots from provenance metadata. Retain only the technical source/lineage relationships required for copy tracking and lineage restrictions; do not expose deleted profile data through those relationships. Do not automatically rewrite text the author explicitly authored inside copied test content.

On confirmed account deletion, immediately deny access to all of that user’s Learning attempt answers/results and remove them on the next successful hourly cleanup, without waiting for the normal three-day result deadline. Preserve open moderation cases and active restrictions. Required technical/audit records retain only an opaque deleted-account identifier, not name, email or avatar; identifier retention follows the relevant record lifecycle. Existing audit records expire at their original one-year deadlines, without renewal from account deletion. This is the Learning policy; integration with the repository-wide account deletion workflow requires separate verification.

## 6. Moderation is a separate permission path

| Privileged action                                                            | Moderator               | Senior moderator                    | Platform administrator | Additional conditions                                                                         |
| ---------------------------------------------------------------------------- | ----------------------- | ----------------------------------- | ---------------------- | --------------------------------------------------------------------------------------------- |
| Review public/unlisted content, including blocked content                    | Yes                     | Yes                                 | Yes                    | Explicit moderation endpoint and audit; Published versions only; unpublished content excluded |
| Review private content                                                       | No                      | No                                  | Yes                    | Published versions only, reason plus audit; no draft access                                   |
| Block one test or topic                                                      | Within authorized scope | Within authorized scope             | Yes                    | Reason, current permission, target checks and audit                                           |
| Preview/confirm a test-lineage block                                         | No                      | Yes                                 | Yes                    | Bounded consistent target set; safe private-descendant projection                             |
| Lift a restriction                                                           | No                      | Yes, within authorized action scope | Yes                    | Specific case/target, reason, fresh role, audit; no implicit lifting of other cases           |
| Permanently delete content                                                   | No                      | No                                  | Yes                    | Separate destructive command and evidence/retention policy                                    |
| Assign/revoke platform role                                                  | No                      | No                                  | Yes                    | Atomic assignment/audit, bootstrap and last-admin safeguards                                  |
| Edit another author's content or read learner answers merely because of role | No                      | No                                  | No                     | No such permission is granted by this feature                                                 |

Unpublished content is visible only to its author under ordinary owner authorization; no platform role, including administrator, grants draft review access. Moderation reviews published versions only, subject to visibility permissions. Private-content review permission never includes unpublished drafts. Blocking may deny the author access but never grants staff draft access.

No moderator, senior moderator or platform administrator may adjudicate a moderation case concerning their own test/topic, lift its restrictions or close its complaint. Another independently authorized staff member must handle the case; there is no administrator override for self-moderation. This does not prevent ordinary permitted owner lifecycle actions such as metadata-only deletion.

V1 platform role management is administrator-only and targets existing registered accounts. Each account has at most one platform role: moderator, senior moderator or platform administrator; changing role replaces the prior role and revocation restores ordinary-user permissions. Assignment/change/revocation require confirmation and a reason, with atomic audit recording. Moderators cannot manage roles; administrators cannot self-elevate or bypass last-active-administrator protection. Arbitrary permission sets and custom roles are deferred. Existing immediate revocation and organization-role separation apply.

Bootstrap the first platform administrator by explicitly configuring the ID of an existing registered account. Do not create an account or auto-select the first user, an organization owner or a demo account. Atomically record one-time bootstrap completion and the audited assignment. Reruns with the same configured ID make no assignment changes; a different ID after completion fails explicitly rather than assigning another administrator. A completed bootstrap never restores a subsequently revoked role. Later administrators are assigned by a currently authorized platform administrator. Reject missing/invalid account selection before any assignment. This documents the proposed seed behavior and does not authorize running it.

Prevent any role removal/demotion, account deletion or deactivation that would leave no active platform administrator, including self-service deletion. Require another active administrator first. Enforce the invariant atomically across concurrent role and account-lifecycle operations so two administrators cannot simultaneously remove the last effective administrators.

Platform role changes/revocation take effect immediately across devices for subsequent privileged operations. Check current permissions for every moderation read and write, including protected-content retrieval; stale sessions or an open page do not preserve privileges. On denial, the UI closes privileged access while preserving the ordinary authenticated session and eligible normal features. Coordinate revocation and privileged mutations transactionally: a mutation committed before revocation remains valid; after revocation commits, no newly authorized privileged mutation may commit using the old role. Previously delivered browser content cannot be retracted. An organization owner/admin receives no platform rights. A moderator acting as a normal learner is still subject to current visibility, blocking and attempt ownership.

Lineage-block preview shows the total affected test count. For published tests the staff member is authorized to inspect, show title, author and status. Private tests without review permission and unpublished copies contribute only aggregate counts, with no titles, authors or content. Draft confidentiality applies even to administrators. If lineage membership changes after preview, reject the stale confirmation and require a refreshed preview and confirmation. Apply existing self-moderation exclusions without granting access to hidden targets.

An individual block affects only that target; a lineage block explicitly creates restrictions for the selected source and descendants. Existing independent copies otherwise stay available under their own policies. A parent-topic block denies its exercises through both topic and direct test routes; it does not itself block independently owned external copies.

Restriction lifting is not republication, undeletion or visibility restoration. If one of two cases is lifted, access remains denied by the other. Lifting a topic restriction does not lift a child's own restriction. Expired/superseded attempts stay terminal. Permanent deletion is not reversible via an unblock command.

The owner may logically delete an eligible blocked test through a metadata-only command. Verify ownership and deletion eligibility without returning the blocked draft, publication, explanation or media. Remove it from the owner's library and ordinary access, retain active restrictions and required moderation evidence, and record the lifecycle action. This is not administrator-only permanent deletion. A currently published embedded exercise still cannot bypass the published-removal guard. Later lifting its block does not undo the owner's deletion.

A blocked topic may be deleted immediately by its owner using the same keep/delete exercise choice, without moderator approval and without opening a new review. The action reveals only authorized lifecycle metadata. Kept exercises become private standalone tests while retaining every applicable topic block and their own restrictions; deleted exercises remain inaccessible. Unrelated independent copies are unaffected.

During deletion, add each active topic case ID as a restriction target on every kept exercise lineage before detaching it. Keep the existing case identity; do not open another case or request a new moderation decision. Removing the topic relation must never create a readable interval. Lifting that case clears its propagated targets; separately opened test cases remain active until independently lifted. Perform propagation, detachment and audit in one transaction, coordinated with concurrent unblocking. All staff draft access is denied and self-moderation is prohibited. Deleted published evidence is retained for open cases/active blocks; 30-day post-case evidence retention and safe aggregate-only hidden-target impact fields are agreed.

For owner-deleted content with an open moderation case or an active restriction, retain the published version under review for authorized moderation access. Enforce the existing role/visibility permissions and self-moderation exclusion; unpublished drafts remain inaccessible to all staff. Owner deletion neither closes the case nor lifts restrictions. Without a case or active restriction, do not create a separate moderation-only content copy; other publication/copy/attempt references retain their own lifecycle rules. Retain moderation-only published evidence for 30 days after the case is closed and all related restrictions are lifted, measured from the later event. While any related case is open or restriction remains active, the evidence remains retained. Reopening a case or applying a related restriction before cleanup suspends evidence expiry. After the eligible 30-day window, remove the moderation-only reference/copy through reference-aware cleanup; do not delete content still needed by publications, attempts or independent copies. Retain minimal moderation/role-action audit records for one year from the action timestamp. Store only actor/target/case identifiers, action, time and reason; no test content, drafts or learner answers. Platform administrators alone may view this audit through authorized operations. Records are immutable to users/staff; lifecycle cleanup removes expired records rather than allowing edits. Active restrictions and required case state have a separate lifecycle and are never lifted by audit cleanup. Apply the agreed account-erasure and opaque-identifier policy.

## 7. Operation concurrency and replay

These are semantic preconditions, not invented GraphQL endpoint names. Exact lock ordering follows the [schema proposal](SCHEMA-AND-DEPENDENCIES-learning.md); final adapter SQL and concurrency tests remain required.

| Operation family                   | Concurrency input / coordination                                                                       | Safe retry behavior                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Create resource                    | Principal-scoped operation identity                                                                    | Same created resource, no duplicate library entry                                 |
| Save draft / reorder / composition | Expected draft/aggregate revision and operation identity                                               | Same accepted outcome; changed payload or stale new write conflicts               |
| Publish test/topic                 | Expected aggregate revision; lock affected membership/content and access state                         | Same publication, never duplicate versions or partial detachments                 |
| Visibility change                  | Expected access revision and operation identity                                                        | Same target access state; cannot replay stale authorization                       |
| Copy into topic                    | Expected destination revision and explicit eligible source snapshot; lineage/access/media coordination | One independent copy; no duplicate exercise or lost media references              |
| Submit completed attempt           | Authorized version binding, operation identity and current access                                      | One completed result per operation; independent tabs do not share mutable answers |
| Delete resource/topic              | Expected resource/membership revisions, explicit exercise choice, operation identity                   | One logical deletion outcome, never scope expansion from a stale confirmation     |
| Block lineage                      | Preview scope revision, operation identity, lineage root/access locks                                  | Scope change requires refreshed preview; no descendant escapes a committed block  |
| Lift restriction / assign role     | Expected case/assignment state, current privilege, operation identity                                  | One audited change; no lost concurrent restriction or role update                 |

Revision failure must not return another user's or a now-blocked resource's draft. A replay still enforces current permission/retention before returning protected outcome data. For deletion, a minimal receipt can acknowledge the caller's own completed command without loading deleted content; it contains only the minimum outcome metadata needed for that acknowledgement.

Retain minimal successful-operation receipts for 12 hours from commit, without answer bodies or authored content. Ticket admission is 12 hours; the receipt replay window is 12 hours from commit. Replays do not renew either deadline or extend result retention. Recheck current access before retrieving the referenced result. A changed payload conflicts. If admission expires without a receipt, or the receipt expires, reject without re-execution.

A copy checks eligibility against the actual snapshot chosen for copying, not only an earlier picker response. A public source that becomes private or blocked before the copy is authorized cannot be copied on the strength of the stale page. Once the copy commits independently, later source deletion/privacy changes do not revoke it; an explicit lineage block can.

## 8. Protected media and retained versions

Authorize a specific content use and projection, not just a known asset ID. Owner draft access, learner-visible publication content, post-submission explanations and authorized moderation are different contexts. A learner cannot retrieve an explanation-only image through an active-attempt context before submission. Reusing an image in already-visible content cannot promise that its bytes are secret.

An old version can be served only through an authorized retained attempt/result or permitted review context. Historical topic membership is evidence of a snapshot, not an access grant. Detached/private exercises, blocked parents and expired results deny old-version media through those now-invalid contexts.

Independent copies retain their own valid media uses. Removing a source use or source account cannot delete bytes still required by the copy. Conversely, another public use of the same bytes does not authorize browsing a private document, its caption or its resource metadata. Cleanup and new-reference creation must coordinate; physical deletion happens only after all required retention references are gone.
