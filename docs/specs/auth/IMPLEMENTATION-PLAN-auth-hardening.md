# План імплементації: автентифікація, авторизація та надійність сесій

Статус: **етапи 9 і 10 локально завершені. Міграції застосовані лише до локальної БД; розгортання та перевірки staging/production відкладені до окремого release-етапу**.
Дата: 2026-09-24. Перевірений Git baseline: `dev`, `02b66278`.

## 1. Мета і підхід

Користувач із придатною refresh-сесією має продовжувати роботу після закінчення access token: під час відкриття сторінки, збереження форми, AJAX, паралельних запитів і роботи у кількох вкладках. Backend повинен незалежно від frontend перевіряти identity, session revocation, resource ownership і tenant permissions.

Спочатку зафіксувати регресії й контракт сесії, потім забезпечити транзакційні backend-інваріанти, підключити всі frontend entry points і закрити решту підтверджених security findings. Завершувати кожен інкремент окремими доказами RED → GREEN → перевірка; не підміняти PostgreSQL/browser перевірки unit-моками.

Цей документ об’єднує знахідки, рішення, залежності та критерії приймання. Наступний крок — окремий план невеликих задач/PR, а не виконання всіх змін одним великим рефакторингом.

## 2. Джерела і достовірність

- [Функціональний аудит поточного dev](../../auth-session-functional-audit.md): SESSION-01…05, реальний Next.js/Chromium із контрольованим upstream; окремий Nest HTTP harness із тестовими repository ports.
- [Попередній security-аудит](../../../../dash-stack-auth-hardening-20260924/docs/auth-security-audit.md): AUTH-01…18, baseline `6e66522d`. Цей файл знаходиться в іншому worktree; посилання локальне. Весь перелік проблем перенесено нижче, тому план не залежить від доступності того worktree.
- При функціональному аудиті повторно звірено незмінені backend auth/invitation/user/storage та перевірені task use cases/repository. Це не означає, що всі нові Vocabulary endpoints пройшли повний security regression.
- **RUNTIME**: сценарій відтворено, але рівень ізоляції зазначений; це не production evidence.
- **CODE**: дефект підтверджено трасуванням коду/локальним регресійним експериментом; live exploit не заявляється.
- **VERIFY**: відома прогалина або ризик, для якого потрібна додаткова перевірка.
- **DECISION**: поведінка існує, але цільова політика ще має бути зафіксована.

Пріоритет P1 — blocker до release; P2 — суттєвий дефект/hardening; P3 — нижчий ризик. Пріоритет описує потребу виправлення, а не автоматично exploit severity. Доведеного P0 authentication bypass немає. Усі пункти нижче відкриті; дублі між SESSION та AUTH не рахувати як різні уразливості.

## 3. Межі роботи

**Включено:** auth/session flows, cookies, JWT, refresh, signup, verification, reset, logout, Auth0, BFF, SSR/actions, клієнтський identity/cache, server authorization, tenant/resource isolation, storage ownership, конфігурація, redaction, rate limiting, CSRF, міграційний і rollout-план, security regression.

**Не включено:** нові бізнес-функції Vocabulary, заміна фреймворків, загальний перепис монорепозиторію, автоматичне додавання MFA/passkeys, зміни production без погодженого rollout. Explicit account linking і transfer ownership не будувати лише для обходу поточних дірок: спочатку безпечно відхиляти ці операції.

Тут змінюється тільки документація. Схеми, міграції, залежності, видалення файлів та CI/infra під час майбутнього виконання проходять правила AGENTS.md. Дозвіл скласти план не є дозволом застосувати міграцію або deploy.

## 7. Що вже працює і має залишитися

- HS256 signature verification відхиляє malformed/expired/wrong-signature JWT; невідомий user відхиляється.
- Один BFF-запит із valid refresh оновлює cookies навіть без access cookie.
- Повторне використання спожитого refresh відхиляється; доказу двох успішних successor sessions немає.
- Tenant guard перевіряє DB membership; MEMBER не задовольняє ADMIN requirement; foreign tenant дає 404.
- Task access scoped за organizationId, assignee membership валідований. Це не закриває foreign label і attachment ownership.
- Parameterized Prisma не дає підстав стверджувати SQL injection через сам факт старого class-validator.
- Vocabulary auth-only owner routes не повинні знову залежати від Organization, sidebar або dashboard layout.

## 8. Цільовий контракт і архітектурні рішення

### 8.1. Session contract

Зовнішні стани: `authenticated`, `unauthenticated`, `unavailable`. Unresolved/loading — окремий frontend стан; `recovering` — внутрішній bounded процес, а не нескінченне очікування.

401 означає остаточну відсутність придатної автентифікації або явно позначений access rejection до виконання handler. 403 — недостатній дозвіл, він не повинен запускати refresh. Timeout/5xx — unavailable, cookies зберігаються. Відновлення максимум один раз на запит/навігаційний цикл; запропоновані error codes узгодити в dedicated contracts, не вважати вже наявними API.

### 8.2. Backend session authority

Пропозиція: server-side session з opaque id, userId, status/revokedAt, absolute expiry; refresh credential hash, generation, consumed/replaced metadata. Конкретні Prisma models/indices визначити після race design. JWT містить session reference і мінімальні validated claims. Guard перевіряє user/session; рекомендація — immediate revocation, вартість запиту й cache invalidation явно описати в ADR.

Rotation, logout, logout-all і reset повинні мати спільний механізм серіалізації: refresh, що змагався з revoke/reset, не може створити живу сесію після успішного відкликання. User-level revoke має охоплювати конкурентне створення сесії за погодженою політикою. Транзакції короткі; hashing, HTTP і SMTP поза ними.

### 8.3. Конкурентність — рішення до frontend implementation

Рішення зафіксовано в [ADR-0001](../../adr/0001-auth-session-protocol.md): стабільний opaque browser session credential із server-side `AuthSession`. Варіанти, які оцінювалися:

- **Зберегти поточні rotating browser cookies:** потрібна координація між інстансами та вкладками, recovery від втрати відповіді, обмежена idempotency/replay policy і захист від out-of-order Set-Cookie. Process-local mutex — лише оптимізація. Не повертати raw successor з DB hash і не вводити безстрокове grace window.
- **Стабільна opaque BFF session cookie, backend tokens зберігаються server-side:** зменшує browser rotation races, але додає session store/операційну складність і змінює архітектуру. Не впроваджувати мовчки як дрібний fix.

Обрано stable session, тому що browser-side rotation не може надійно запобігти rollback cookie через запізнілу відповідь без складного розподіленого протоколу або збереження raw successor. Process-local single-flight залишається лише оптимізацією навантаження.

Неможливо за самим фактом повтору stolen bearer token завжди відрізнити legitimate retry від атаки. Визначити bounded retry window, scope replay revocation і failure behavior; ці компроміси не приховувати під словом mutex.

### 8.4. Frontend boundaries

Shared server-only session transport не імпортує features/entities. Domain/session orchestration — backend ports/use cases; cookie writing — Route Handler/Server Action. Thin App Router adapters. Runtime Zod contracts — dedicated `*.schema.ts`; без `any`, клієнтських токенів і секретів у props.

SSR recovery не пише cookies під час render. Повернення тільки на validated same-origin path, без credential URL і redirect loops. Окремо спроєктувати CSRF-safe recovery: автоматичний cross-site GET або Next prefetch не повинен самовільно запускати state-changing rotation. Recovery page + same-origin POST/Action — кандидат для ADR.

### 8.5. Політики за замовчуванням для планування

- Заборонити implicit OAuth linking та OWNER invitations; не додавати нові UI workflows без потреби.
- Profile PATCH не змінює email. Verified email-change flow — окремий подальший scope, якщо потрібен продукту.
- Приватні task attachments відокремити від public avatars; спочатку підтвердити класифікацію файлів.
- Усі існуючі sessions не скидати мовчки. В ADR/migration plan вибрати сумісний перехід або погоджений одноразовий re-login.
- CSRF — точна origin policy на BFF і Nest; missing Origin/server-to-server authorization визначити явно, не довіряти довільним X-Forwarded-*.

## 12. Міграції, rollout і сумісність

- Нові session/file ownership поля додавати інкрементально; merged migrations не редагувати.
- Визначити перехід plaintext→hash без двозначного lookup і без приймання digest як credential. Не зберігати raw refresh постійно задля retry convenience.
- Legacy file ownership не виводити лише з переданого key. Ambiguous/unowned data не видаляти; план backfill/quarantine/access policy до ввімкнення enforcement.
- Existing OWNER invites, unverified linked OAuth accounts, email normalization collisions та long bcrypt passwords мають окремі compatibility checks; не виконувати silent account merge чи масове видалення.
- Порядок deploy: additive schema → compatible backend/session contracts → frontend → enforcement/backfill → пізніше cleanup. Якщо mixed versions небезпечні, документувати coordinated rollout/re-login, не імітувати zero downtime.
- Rollback не повинен відновлювати revoked sessions або повертати hashed credentials у plaintext. Перевірити forward-fix/re-login strategy.
- Документувати Auth0 allowed callbacks/grants, secrets rotation, HTTPS/cookie scope, CORS, proxy trust, cluster rate limits і session coordination availability.

Для кожної задачі потрібні: пов’язані IDs; актуальний baseline; scope/files; залежності; опис before/after; RED сценарій; acceptance criteria; validation commands; migration/deploy impact; явні non-goals; доказ завершення.

## 14. Поточний статус

Реалізація розпочата 2026-09-24:

- 2026-09-26 локально застосовано дві підготовлені міграції `20260924173000_add_auth_sessions` та `20260924194000_add_stored_file_ownership` до `dash-stack-db`/`public` на `localhost:5432`; без reset/seed. Це не production deployment.

- BFF об’єднує паралельний refresh з тим самим credential у межах одного Next.js процесу;
- refresh 5xx/network повертає `SESSION_REFRESH_UNAVAILABLE`/503 і не стирає cookies;
- сам refresh cookie більше не закриває доступ до sign-in/sign-up;
- [ADR-0001](../../adr/0001-auth-session-protocol.md) обирає стабільний server-side session protocol для multi-instance correctness.
- додано additive `AuthSession` schema/migration із SHA-256 hash credential; raw credential у БД не зберігається;
- нові access JWT містять `sessionId`; guard перевіряє required claims, ownership, expiry та revocation;
- refresh повертає той самий session credential, а legacy rotating refresh token одноразово обмінюється під час compatibility window;
- logout, logout-all і password reset відкликають нові sessions та очищають legacy refresh tokens.
- shared refresh transport використовується BFF і middleware; expired/missing access відновлюється до SSR render або Server Action, а нові cookies підставляються також у поточний request;
- terminal recovery failure очищає cookies і повертає захищені dashboard/Vocabulary owner routes на sign-in із validated internal redirect.
- login/verify/refresh/OAuth endpoints і Server Actions більше не серіалізують access/refresh credentials у browser-visible JSON; credentials передаються лише через `HttpOnly Set-Cookie`, а Next server transport переносить їх на frontend origin;
- logout revocation failure більше не маскується як success; frontend гарантовано очищає local cookies, а direct Nest controller очищає їх лише після успішного revoke;
- створення та приймання invitations із роллю `OWNER` заборонено одночасно transport і domain policy, включно з legacy pending invites.
- accept invitation умовно споживає лише pending, unexpired запис із тим самим email/org/role як перший запис Prisma-транзакції; membership створюється після успішного consume, а програний parallel accept не створює доступ;
- revoke invitation видаляє лише pending запис у поточній організації; якщо accept уже виграв гонку, revoke повертає помилку замість хибного success. LIFE-08 пройшов PostgreSQL regression: два accept дають один membership, accept/revoke не можуть обидва завершитися успіхом, а failed membership insert відкочує consume і залишає запрошення придатним для наступного accept.
- invitation credentials переведено на 256-bit random raw token із SHA-256 digest у наявному `Invitation.token` за [ADR-0003](../../adr/0003-invitation-credentials.md); create/list API не віддають raw token або digest, а accept приймає token у POST body;
- email invitation веде на чинний `/accept-invite` маршрут; на credential pages і redirects runtime Next повертає `Referrer-Policy: no-referrer`; SMTP failure прибирає pending invite, а подвійний delivery/cleanup failure має окрему помилку;
- старі локальні CUID invitation links несумісні з новим lookup (тестові дані, без deployment); LIFE-21 ще потребує real SMTP/browser/direct-HTTP перевірки.
- profile PATCH більше не приймає email; frontend показує поточну адресу read-only до появи окремого verified email-change flow;
- Task create/update validate tenant-owned labels before mutation; the task transaction now locks the scoped label row through the write. PostgreSQL regressions cover deletion after preliminary validation, foreign labels, and valid labels.
- local storage delete відхиляє traversal, absolute, backslash і percent-encoded keys до filesystem access;
- підготовлено additive `StoredFile` schema/migration; нові uploads записують owner/kind/size/MIME, а failure metadata write компенсується видаленням object;
- create/update task транзакційно bind-ять лише нові `ATTACHMENT` keys поточного actor; conditional bind закриває конкурентне повторне використання одного key;
- фізичне видалення отримує allowlist із `stored_files.taskId`; foreign, shared та untracked legacy keys не передаються storage provider, а legacy objects залишаються в quarantine;
- AUTH-05 PostgreSQL races and storage-failure injection now cover one-winner attachment binding, foreign/image keys, single and bulk task deletion, failed physical deletion, pending-key rebind denial, and parallel task updates. Private serving, legacy quarantine policy, and production cleanup scheduling remain open.
- signup, login і reset-password відхиляють пароль понад 72 UTF-8 bytes на frontend і backend; рівно 72 bytes дозволено, а старим long-password accounts потрібен password reset.
- reset password умовно споживає ще чинний token, оновлює password і відкликає `AuthSession` та legacy refresh tokens в одній Prisma-транзакції; concurrent loser не виконує writes;
- нові email-verification і password-reset credentials мають 256-bit entropy; raw token надсилається лише email-каналом, а в `VerificationToken.token` зберігається SHA-256 digest;
- email verification умовно споживає token, виставляє `emailVerified` і створює `AuthSession` в одній Prisma-транзакції; concurrent loser не отримує нової сесії.
- OAuth приймає лише runtime-validated `/userinfo` payload із `email_verified === true`; login існуючого користувача дозволений лише за точною provider identity, а implicit linking за збігом email заборонено без створення account/session.
- Auth0 `/userinfo` має 5-секундний timeout і typed unavailable/invalid-response errors; довільний credential більше не повторюється як authorization code, а provider response/error details не потрапляють у логи.
- AUTH-02 реалізовано в коді через [ADR-0002](../../adr/0002-oauth-code-flow.md): Next start/callback використовують одноразовий state, PKCE S256 і HttpOnly flow-cookie; Nest обмінює code із фіксованим redirect URI; старий access-token endpoint більше не видає сесію. Live Auth0/browser acceptance, два реальні OAuth tabs і tenant configuration ще не перевірені.
- LIFE-20 частково перевірено direct Nest HTTP: malformed refresh body (`null`, object, array, number, boolean), oversized token і некоректний logout cookie отримують 4xx до виклику use case; invalid body token не обходиться коректним cookie, а cookie-only refresh працює. Відсутній refresh token повертає 401; решта DTO/query/claim матриці ще відкрита.
- logout-all очищає cookies тільки після успішного server-side revocation; failure path перевірено регресією.
- LIFE-04: JWT extractor тепер відхиляє одночасні access cookie та Bearer credential; окремі cookie/Bearer шляхи й malformed cookie перевірено unit-тестами. Ізольований Nest HTTP test із реальними Passport JWT guard/strategy підтвердив 200 для валідних cookie-only і Bearer-only та 401 для змішаного запиту до session lookup; у тесті підмінені session/user ports і cookie parsing. Повний AppModule/DB runtime ще не перевірений.
- LIFE-10: BFF читає request body з верхньою межею до повного буферизування і повертає 413 до upstream для завеликого declared або chunked body. Межі: 5 MiB за замовчуванням, 1 MiB для URL-encoded, 11/51 MiB для image/file multipart із запасом на envelope; proxy-тести перевірили chunked JSON без Content-Length, ранню відмову за Content-Length та дозволений image upload. Production Next HTTP підтвердив 413 для 6 MiB chunked JSON до upstream; client abort під час повільного upstream закрив його відповідь до завершення. Headless Chromium через production Next підтвердив `AbortError` для перерваного `/api/proxy/slow`, закриття upstream без відповіді й 413 `PAYLOAD_TOO_LARGE` для 6 MiB browser POST; multipart edge cases ще відкриті.
- AUTH-17: proxy канонізує кожен path segment, відхиляє encoded/double-encoded structural symbols і окремо кодує легітимні segments перед upstream; upstream fetch не слідує redirects і повертає 502 на 3xx. Unit regression перевірила шлях та redirect; production Next HTTP повернув 400 для `%252e%252e`, `%2f%2fevil.test` і `%255c`. Повна encoded/query матриця та fixed-host перевірка ще відкрита.
- AUTH-13 частково: frontend env schema вимагає явний `API_URL` у production і HTTPS для нелокального backend; localhost/loopback HTTP дозволений для локального production build. Proxy використовує перевірене значення без мовчазного production fallback. Backend key/origin/TTL validation і deployment secret rotation ще відкриті.
- AUTH-13 backend: `ConfigModule` тепер на старті production вимагає JWT access secret щонайменше 32 символи без placeholder, явні додатні access/refresh TTL, `FRONTEND_URL` і CORS origins із HTTPS (або loopback HTTP для локального запуску). Unit-тести перевірили negative/positive випадки; фактичний production boot із порожнім secret завершився до старту сервісу без значення secret у помилці. Інші env-контракти та key rotation ще відкриті.
- AUTH-07 частково: `login`, `signup` і `forgot-password` тепер мають активний `ThrottlerGuard` та квоту на SHA-256 хеш нормалізованої email-адреси, не на спільний IP Next BFF. Nest HTTP regression підтвердила 429 і `Retry-After`, ізоляцію двох адрес та неможливість обходу login-квоти підміною `X-Forwarded-For`. `verify-email`, `reset-password` та `oauth/code` тепер мають активний `ThrottlerGuard` із квотою за SHA-256 digest одноразового token/code. Nest HTTP regression спершу отримала 200 на шосту спробу, після виправлення — 429 із `Retry-After`; інший credential не блокується, а `X-Forwarded-For` не скидає квоту. Це обмежує повтори одного credential, але не масовий перебір різних token/code; `refresh` тепер має окрему квоту 20/min за SHA-256 digest body або cookie credential; Nest HTTP regression спершу отримала 200 на 21-й повтор, після виправлення — 429 для обох transport, при цьому 10 паралельних запитів однієї сесії та інша сесія проходять. Ліміти інших auth endpoint, загальна квота для різних адрес/credentials, trusted-client topology та спільне сховище для кількох Nest-інстансів ще відкриті.
- Етап 3, PostgreSQL evidence: обмін старого refresh-токена умовно споживає його й створює нову `AuthSession` в одній Prisma-транзакції; паралельний обмін дає одну сесію, а failed insert відкочує consume. Десять паралельних refresh нової stable session повертають той самий credential і не створюють нових сесій; logout відхиляє наступний refresh, logout-all відкликає обидві session і прибирає legacy token. Refresh-vs-logout/reset, два Nest і два Next процеси перевірені нижче; aborted-request/browser matrix ще відкритий.

### Cached identity background-refetch regression — 2026-09-28

CodeRabbit finding відтворено двома RED tests: cached authenticated identity переходила в ERROR після 503, а активна Match-сесія втрачала playing state. `useCurrentUserState` тепер використовує останню resolved identity (`User` або `null`) перед перевіркою query error. Помилка початкового завантаження без identity залишається ERROR; справжній 401 перезаписує cached user на guest. Query-level error залишається доступною через `useCurrentUser`/refetch result; cached identity не є дозволом на backend operation. Регресія Match перевіряє ту саму session після помилки й успішного відновлення refetch, без повторного server session creation.

Валідація цього increment: focused 2 files / 16 tests; full frontend 175 files / 794 tests; typecheck, lint (0 errors, 3 попередні warnings), FSD, scoped Prettier і `git diff --check` — PASS. Browser/e2e для цього increment не запускалися.
